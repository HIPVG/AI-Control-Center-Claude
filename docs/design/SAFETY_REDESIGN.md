# 安全装置の再検討と再設計案（ACC-GUARD ほか）

作成: 2026-09-29（JST） / ブランチ: `redesign` / 状態: **判断済み（9章）。1〜8章は提案時の記録として残す**

事実の確度を次の記号で示す。OBSERVED（実測）、REPORTED（引き継ぎメモ等の報告）、
INFERRED（根拠から推論）、UNKNOWN（未確認）。

## 1. 結論

現行の ACC-GUARD は、**「セッション内のフックに承認・受入の権限を持たせる」構成**である。
この構成は、今の運用環境では安全装置として成立していない。バグを個別に直しても解決しないため、構成から改める。

- 承認と受入は、AI の手が届かない場所（GitHub のブランチ保護、PR、CI、人間のマージ）に移す。
- セッション内の仕組みは「事故防止のガードレール」に格下げし、小さく、止まりにくくする。
- 作業カードは JSON の機械検証をやめ、PR 本文とする。記載項目は現行カードの8項目を引き継ぐ。
- この順序で本番運用に入る前に、実セッションで「効いていること」を確かめる試験を必ず行う。

## 2. 環境の変化で何が変わったか

| 項目 | 旧想定（Windows ローカル） | 現在（クラウドセッション＋`redesign`） |
|---|---|---|
| 作業場所 | 人間の PC 上のリポジトリ | 使い捨てのクラウドコンテナ（壊れても再 clone で戻る） |
| 外に残る影響 | ローカルファイル、git、ネットワーク | **git push、ネットワーク、コネクタ（Drive 等）、連携した PC** に限られる |
| main | Claude が扱う対象 | ChatGPT 側の作業ブランチ。Claude は触れない |
| 人間の承認操作 | 別端末で `acc.py activate` | チャット、又は GitHub 上の操作 |

守るべき境界は「どのファイルを編集してよいか」ではなくなった。
中心は「**コンテナの外に何が出ていくか**」である（INFERRED）。
コンテナ内のファイル破損は元に戻せる。一方、push・送信・外部書き込みは戻しにくい。

## 3. 現行 ACC-GUARD の実測結果

実リポジトリの複製に対してフックを直接起動して確認した（OBSERVED）。
`tools/selftest_guard.py` の 27 項目はすべて合格している。つまり、以下はいずれも既存の試験では検出されない穴である。

### F1. このセッションではフックが一度も動いていない（OBSERVED）
- `.acc/`（監査ログの置き場）が存在しない。
- `settings.json` の deny 規則と `DENIED_CMD` はどちらも `git push` を禁じている。それでも本日の `git push origin redesign` は通った。
- プロジェクト設定のフックは、セッションの開始位置によっては読み込まれない。今回はリポジトリ外で開始して後から clone した（INFERRED）。
- **安全装置が効いていないことを知らせる仕組みがない**。CLAUDE.md は「ガードがある」前提で書かれている。この状態は、ガードが無いことを前提にするより危険である。

### F2. バグ2の原因はフックの呼び出し方（OBSERVED・原因特定）
- フックの起動コマンドは `python .claude/hooks/acc_guard.py` という相対パスである。
- `cd` で別ディレクトリへ移ると Python がスクリプトを開けず、`can't open file` で**終了コード 2** を返す。
- Claude Code では、終了コード 2 は「ブロック」を意味する。このため、以後は**すべての**ツール呼び出しが拒否される。
- これとは別に、ガードは作業ルート外への書き込みを設計上すべて拒否する。フックはセッション全体に掛かるため、無関係なパス（`/home/claude/` 等）も巻き込む。
- 以上から、メモにあった「Claude Code 側の問題」という推測は誤りである。公式文書は `${CLAUDE_PROJECT_DIR}` による絶対指定を推奨している。

### F3. バグ1の修正で、AI が自分で承認・受入できるようになった（OBSERVED）
- 有効カードも STOP もない状態で、次のコマンドがフックを通過した。
  - `python3 tools/acc.py resume --by human`
  - `python3 tools/acc.py accept ... --kind independent --by human`
- `settings.json` の deny は `python tools/acc.py` という形だけを対象にしている。`python3 ...` や `py ...` は一致しない（INFERRED、前方一致規則のため）。
- 承認者名は `--approve-as` の自己申告である。**人間の承認という境界は、実質的に約束事に過ぎない**。
- 状態ファイル `.acc/` も、AI が Bash で書ける場所にある。

### F4. 「読み取り専用」として常時許可しているコマンドが、読み取り専用ではない（OBSERVED）
- `find . -name *.py -delete`（ファイル削除）
- `git branch -D main`（ブランチ削除）
- `git diff --output=backend/app.py`、`git log --output=CLAUDE.md`（保護対象ファイルを含む上書き）

### F5. 通常作業を止めすぎる（OBSERVED / REPORTED）
- パイプ、`&&`、リダイレクトを含む Bash はすべて拒否される。
- 作業ルート外への書き込みもすべて拒否される。
- フックが異常終了した場合も、フェイルクローズで全面停止する。
- 結果として、単純な片付けに数時間かかり、設定の無効化で回避することになった（REPORTED）。
  **止めすぎる安全装置は、外される**。

### F6. 受入が「同じ主体の中」で閉じている（OBSERVED）
- `tests/acceptance/` は空である。CI（`.github/`）もない。
- `verify` の証拠は `.acc/` に保存されるが、`.acc/` は `.gitignore` 対象なので、人間や他の主体からは見えない。
- verifier サブエージェントは同じモデル・同じセッションの延長であり、独立確認にならない。これは SETUP.md 自身が認めている。

### F7. 正規表現による禁止リストは原理的に抜けられる（INFERRED）
- `allowed_commands` は前方一致である。そのため `python` を許可すると、`python -c "import shutil; ..."` のような任意の操作も通る。

## 5. 再設計案：3層構成

### 層1　外部境界（強制力あり・AI から変更できない）
承認と受入の権限は、すべてここに置く。

- **ブランチ保護（GitHub の ruleset）**。人間が設定する。Claude には設定させない。
  - `main`：Claude の資格情報では push できないようにする。force push と削除も禁止する。
  - `redesign`：force push と削除を禁止する。PR 経由のマージだけにするかは、判断 D2 で決める。
- **CI（GitHub Actions）**：`redesign` 向けの PR と push ごとに、次を実行する。
  - `pytest`（legacy/ を除く）
  - `tests/acceptance/`
  - 保護対象パスの差分検査。変更があれば「人間確認が必要」の印を付ける。
  - これが実装担当とは別の主体による機械確認であり、独立確認の最低ラインになる。
- **受入 = 人間による PR のマージ（又は承認）**。
  - `acc.py accept` と `.acc/acceptance/` は廃止する。
  - 受入の記録は、PR と CI の結果として GitHub に残る。

### 層2　セッション内ガードレール（事故防止・小さく・止まりにくく）
目的は「うっかり」を防ぐことであり、権限の境界ではない。そう明記する。

- **公式の権限設定（`permissions.deny`）を主に使う**。
  - 対象例：`git push origin main` 系、`--force`、`git reset --hard`、`git branch -D`、`git clean`。
  - フックの `allow` では deny を上書きできないことが公式文書で確認できている。
- **フックは保護対象パスの書き込み拒否だけに絞る**。対象は `.claude/**`、`tests/acceptance/**`、`docs/WORKING_RULES.md`。
  - 起動は `${CLAUDE_PROJECT_DIR}` を使った絶対パスで行う（F2 の対策）。
  - 対象外のパスとツールはすべて素通しにする（F5 の対策）。
  - フック自身が異常終了しても、全面停止にはしない。保護対象への書き込みだけを拒否する。
- **ガードが効いていることを見えるようにする**。
  - SessionStart フックで「ガードレール有効」を表示する。
  - 作業開始時に既知の拒否を1回試して、確認する（カナリア試験）。
  - ガードが効いていないと分かった場合は、作業を止めず、その旨を報告して層1に頼る。

### 層3　手続き（カード・証拠・停止）
- **作業カード → PR 本文**。
  - 現行8項目（目的、対象と現状、判断者、権限と費用、主体と権限、確認と証拠、停止と復旧、結果と残課題）はそのまま使う。
  - JSON スキーマ、ハッシュ固定、`activate` は廃止する。承認はチャットでの人間の指示、又は GitHub 上の操作とする。
- **確度表示・2回失敗で設計へ戻る・判断依頼書**：CLAUDE.md の規則として残す。これらは機械では強制しない。
- **停止**：チャットでの「止めて」とセッション停止を正とする。無人実行（予定タスク）を使う場合に限り、GitHub 上の停止スイッチを別途検討する。
- **連携 PC（Windows）での作業**：連携経由の削除は既定で人間の許可が必要である（プラットフォーム側の制約）。それ以上の保護は、使う段階で別途設計する。

### 廃止・移動するもの（legacy/ へ）
- `.claude/hooks/acc_guard.py`、`acc_common.py` の大半
- `tools/acc.py`、`tools/selftest_guard.py`
- `.acc/`、`work-cards/`（JSON カード、TEMPLATE）
