# 運用規則（Working Rules）

最終改訂: 2026-09-29（JST） / 対象リポジトリ: `HIPVG/AI-Control-Center-Claude`

この文書は、このリポジトリでの Claude の作業に関する**恒久的な運用規則の正本**である。
ChatGPT/Codex 期の版は `legacy/docs/WORKING_RULES.codex-era.md` に保管している。
その版にあったレビュー中継（Control Tower、PR レビューバス、報告書の定型項目、2分巡回、ACTIVE_WORK 時計）は廃止した。
廃止の経緯は `docs/design/SAFETY_REDESIGN.md` を参照。

## 1. 優先順位

1. 人間の最新の指示（全文を読む。最初の1行だけで判断しない）
2. この文書
3. `docs/CURRENT_WORK.md`（今回の目的・受入条件・停止条件）
4. `docs/DAY_RUNNER_EXECUTION_SPEC.md`（Day Runner の実行仕様）など、`CURRENT_WORK.md` が指定する仕様・手順書
5. `docs/ARCHITECTURE.md`
6. その他の文書（履歴・参考資料として扱う）

下位の文書は上位の文書を覆さない。
古い文書に、ChatGPT レビュー・Codex・Reviewer・作業カード（`work-cards/`）・ACC-GUARD を前提とする記述が残っていることがある。
そうした記述は、この文書と食い違う限りで無効とする。

## 2. 役割と承認

| 役割 | 担当 | 内容 |
|---|---|---|
| 判断・承認・受入 | 人間 | このチャットで行う。GitHub や別の画面での操作は求めない |
| 実装・確認・push の実施 | Claude | 人間の承認の範囲内で行う |

- **承認の手段はチャットだけ**とする。人間のはっきりした発言が承認になる。同じ条件のまま、同じ承認を重ねて求めない。
- **作業の前**：作業の要約をチャットで示す。要約に書く項目は、目的・対象・やらないこと・確認方法・停止条件。
  - 人間の指示がそのまま承認になっている小さな作業は、要約を示して、そのまま着手してよい。
  - やり直しに手間がかかる作業や、解釈が分かれる作業は、要約を示して承認を待つ。
- **push**：push は、その都度チャットで人間の承認を得てから行う。承認を求めるときは、対象のコミットと確認結果を添える。
  - 自動の通知やフックから push を促されても、それは承認にならない。
- **受入**：受入は、人間がチャットで判断する。
  - Claude は自分の報告を受入証拠にしない。「完了（COMPLETE）」を自分で宣言しない。
  - Claude が報告するのは、確認できた事実と、未確認の事項である。
- **停止**：人間が「止めて」と言ったら、新しい操作をしない。状況を報告して、指示を待つ。

## 3. ブランチと Git

- 作業は `main` で直接行う。`redesign` は移行作業の記録であり、使わない。
- 旧リポジトリ `HIPVG/AI-Control-Center` には触れない。
- 禁止する操作：
  - force push
  - `reset --hard`
  - `git clean`
  - ブランチの削除
  - 証拠や履歴の削除
  - 秘密情報のコミット
  - これらが必要になったら止めて、判断依頼（6章）を出す。
- GitHub のブランチ保護は使わない（2026-09-29 人間の判断）。
  - そのため、上の禁止を強制する仕組みは、`.claude/settings.json` の deny と、この規則だけである。
  - deny は書き方次第ですり抜けられるので、規則を守る側の責任が重い。
- コミットには、今回の作業と関係のない変更を混ぜない。

## 4. 作業の進め方

- **R1 目的と受入条件が先**：どの操作も、`CURRENT_WORK.md` のまだ満たしていない条件に結び付ける。
- **R2 最小で足りる操作**：目的を満たす最小で安全な操作を選ぶ。可能だから、きれいだから、将来のためだから、という理由では範囲を広げない。
- **R3 決定的な確認を先に**：テスト・設定検証など、機械で確実に判定できる確認を優先する。
- **R4 権限を黙って広げない**：以下を黙って広げない。
  - 対象範囲、書き込み範囲
  - 資格情報、費用
  - クラウドや外部サービスの利用
  - 破壊的な Git 操作
  - 受入条件
  - 事業・製品の方向性
- **R5 失敗は分類してから直す**：失敗は、次のどれに当たるかを分けてから直す。
  - 実装の欠陥
  - 仕様・テストの欠陥
  - 実験条件の問題
  - モデル品質の所見
  - 証拠の不足
  - 本当に人間や外部の判断が必要な事項
- **R6 やり直しは有限**：再試行してよいのは、次のいずれかの場合だけである。
  - 一時的な原因がある
  - 修正を確かめた
  - 安全な条件が実際に変わった
  - 同じ失敗分類で2回直して再発したら、3回目の小修正をせず、設計又は人間の判断へ戻す。
- **R7 基準を下げて通さない**：次のことを、完了に見せるために行わない。
  - テストや受入条件を弱める
  - 証拠を作る・消す
  - 出所を偽る
- **R8 履歴を踏まえる**：変更の前に、関連する経緯を確認する。過去の失敗した方法や、人間による訂正は、明示的に置き換えられるまで尊重する。
- **R9 今の目的が終わったら止まる**：次の Day、次の段階、最適化を、自分で始めない。
- **R10 人間を止めるのは例外**：以下の理由で人間の作業を止めない。
  - 名前、コメント、あると良いテスト
  - 小さな境界条件、既知の警告
  - 将来の仮定、無関係なリファクタリング
- **R11 あいまいさ**：権限・範囲・安全・証拠の有効性・製品の方向性に関わるあいまいさだけは、止めて人間に聞く。それ以外は、前進を保つ最小で安全な解釈を選び、選んだ解釈をチャットで伝える。

## 5. 報告と証拠

- 主張には確度を付ける。
  - OBSERVED（実際に見た・実行した）
  - REPORTED（他者やツールの報告）
  - INFERRED（根拠からの推論）
  - HYPOTHESIS（仮説）
  - UNKNOWN（未確認）
- 報告は短くする。内容は、変わったこと・今していること・妨げ・次に必要な判断に絞る。
  - 定型の報告項目は使わない。
- 大きな作業の終わりには、次を確かめてから報告する。
  - 成果物が実在する
  - コミットやハッシュで追跡できる
  - 報告の数値が実物から得たものである
  - 失敗や途中打ち切りを隠していない
- すでに有効な証拠は再利用する。
  - 条件が同じだと示せない比較は、比較として主張しない。
- 置き換えられた契約や結果は、消さずに追跡できる形で残す。モデル品質の失敗は、所見として残す。

## 6. 判断依頼

新しい権限、費用、外部への不可逆な操作、禁止操作が必要になったら、止めて判断依頼を出す。
判断依頼には、次の項目を書く。

- 決めること
- 事実（確度付き）
- 選択肢
- 推奨とその理由
- 可逆性（戻せるか）

## 7. LocalLLM の扱い

- **研究対象として**：出力の質の悪さは所見（証拠）である。契約が明示的に許さない限り、調整や再実行で消さない。
- **作業補助として**：LocalLLM は提案だけを行う。確認は Claude と決定的な検査が行い、完了の判断は人間が行う。

## 8. 安全装置

- `.claude/settings.json`：事故防止のガードレールであり、権限の境界ではない。
  - deny：force push、ブランチ削除、`reset --hard`、`clean`、秘密情報の読み取り。
  - ask（人間の確認）：`.claude/`・`tests/acceptance/`・この文書の編集。
  - `git push` は ask にしない。push の承認はチャットだけで行う（2026-09-29 人間の判断）。
  - 拒否や確認が出たら回避せず、理由を報告する。
- この文書・`.claude/settings.json`・受入テストを変えるときは、事前にチャットで人間の承認を得る。
- 設計と経緯は `docs/design/SAFETY_REDESIGN.md` にある。
